Safeguarding Evidence Processing: design system

The single source for the application's look and behaviour. Every screen uses these tokens and components; the same stylesheet (app.css) styles this page and the application. Values on this page are illustrative. In the application every number, ID and status comes from the package service, the review workflow, the reconciliation adapter or the audit log.

Open the application
Design principles

1. Trust over decoration. Light surfaces, one restrained blue-teal accent, semantic colour only for state. 2. Traceable by default. Every figure names its source (file version, SHA-256, audit event, engine output). 3. Honest state. Progress is shown only as real counts or as an indeterminate bar while the engine runs. A stage is completed only when a backend result or a recorded event says so. 4. Explicit control. Activation and rejection are confirmed in a dialog. Analyst decisions always carry a reason and the TEST-ONLY authority is always visible. 5. Readable data. Tabular figures, monospaced identifiers and hashes, right-aligned amounts, negative amounts in red.

10 · Navigation and screen inventory

Persistent sidebar in four groups (Workspace · Review & control · Reconciliation · Governance). The top bar holds breadcrumbs, the current-package selector and the environment pills. Screens that act on a package are disabled until a package is selected. Every screen below is implemented and reads live data from the API named.

1 · Overview dashboard

#/overview

Current package facts (files received, identified, validated, review, missing / failed, validation, activation, latest reconciliation), next-step callout, recent packages. GET /api/packages, /api/packages/{id}

2 · Evidence intake

#/intake

Reporting period, drag-and-drop of files or a ZIP, a staged file list (name, size, type, SHA-256, optional declared category, remove), then submit. POST /api/staging, /api/packages, /api/packages/{id}/intake

3 · Processing centre

#/processing/{job}

Nine pipeline stages with status, times and evidence; the real file count; per-file results; a live feed of recorded events. GET /api/jobs/{id} (polled)

4 · Evidence classification and file status

#/packages/{id}

One row per evidence slot: category, file, identified by content or declared, route, status, reason, next action; refused uploads. GET /api/packages/{id}

5 · Column mapping and analyst review

#/review · #/review/{pkg}/{version}

Queue with diagnosis. Review grid: position, source column, sample values, proposed field, assessment, validation, financial / sign flags, decision. The expanded row shows statistics, provenance, field definition and the actions Map / Change / Use as source / Ignore / Leave unresolved, each with a reason. Complete or Reject (confirmed). GET/POST /api/review/…

6 · Package validation (PV-01 to PV-09)

#/validation/{id}

The check table (result, evidence, blocks activation, required action), slot summary, status legend, and the selection that would be snapshotted. GET /validation, POST /validate

7 · Activation confirmation

dialog on #/validation/{id}

Enabled only when the last validation passed. The dialog states the package, versions, snapshot effect and that there is no submission or audit pack. Then the result: snapshot, status and next steps. POST /activate {confirm:true}

8 · Package history and file versions

#/history/{id} · #/history/{id}/{version} · #/snapshot/{id}/{snap}

Snapshots, validation runs, every version (intake, SHA-256, status history, previous version, replacement reason), review decisions, handoff checks, recorded events. GET /history, /versions/{v}, /snapshots/{s}

9 · Correction and resubmission

#/resubmit/{id}

Each category awaiting correction (status, reason, missing fields, what to correct), upload of the corrected file with a reason, and upload of missing evidence. POST /resubmit, /intake

10 · Reconciliation execution

#/reconciliation/{id}

Eligibility (active snapshot = current selection, engine configured), a run button, four real run stages, outcome totals and previous runs. POST /reconcile, GET /jobs/{id}

11 · Reconciliation results dashboard

#/runs/{run}

Status, total, PASS, FAIL, insufficient, N/A, exceptions by severity; tabs for exceptions, control results (filterable), the validation report, and inputs with integrity. GET /api/runs/{run}

12 · Exception investigation

#/runs/{run}/exceptions/{exc}

Description, financial impact, account, dates, supporting evidence resolved to file version / line / row, associated control results, investigation group. All values are as written by the engine. GET /api/runs/{run}/exceptions/{exc}

13 · Activity and audit timeline

#/activity/{id}

The hash-chained audit log, verified on load and grouped by day, with type filter, actor, IDs and the recorded details. GET /api/activity

Meaningful state names used across the application: Initialising · Identifying evidence categories · Mapping recognised fields · Requires review · Package validation · Ready for activation (all PV checks pass) · Active · Reconciliation complete (CLEAN / Exceptions open / Evidence incomplete).
