The failure mechanism is in the backend code:
1. `cases._begin_run` calls `context.stage`.
2. `zipfile.ZipFile.read` raises `BadZipFile("Bad CRC-32 …")`. Only the constructor's `BadZipFile` is mapped to `INVALID_ZIP`.
3. `_begin_run`'s `except Exception` records the run as FAILED (code `RUN_FAILED`). The intake job is never created.

This is deterministic, and it is independent of the AI and of the data.

**Side effect (harmless):** members read before the corrupted one are staged as inert staging entries in the workspace on each attempt.

## What did not work / caveats

- **Nothing failed.**

- Workspaces `C:\u42v\rfdata_ws_1..4` were left in place for inspection. They can be deleted.
